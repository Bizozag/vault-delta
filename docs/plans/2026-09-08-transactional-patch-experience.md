# 补丁生成、应用与恢复体验设计和验证记录

日期：2026-09-08

对应实施计划：Task 20。

## 目标与范围

本阶段把已有的补丁构建、包检查、基线验证、事务应用和回滚能力接入 Avalonia Desktop。比较页可以从完整 `CompareResult` 生成默认 ZIP；补丁页可以打开 ZIP、检查目标库、应用补丁，并从独立 Journal 恢复事务。

核心安全算法仍位于 Domain、Application 和 Infrastructure。Desktop 只通过服务接口编排工作流，不直接读取补丁 ZIP、不计算哈希、不修改目标文件，也不重新实现事务语义。本阶段不新增公开 CLI、云端传输、账号或后台同步。

## 生成 Gate

比较完成且确实存在变化时启用“生成 ZIP 补丁”。生成流程：

1. 用户选择最终 `.zip` 路径。
2. 使用比较阶段保留的 baseline、target 和完整 `DiffSet` 构造 manifest v1。
3. 从新快照目录读取 Added 和 Modified 载荷。
4. 在临时目录生成目录包，再压缩为临时 ZIP。
5. 使用 ZIP Reader 与 Package Inspector 重新验证清单、载荷哈希、文件数和字节数。
6. 全部通过后才把临时 ZIP 发布为最终文件。

失败时不会留下可误用的最终补丁。默认文件名包含本地时间戳；已存在的输出路径由 writer 拒绝，避免静默覆盖。

## 应用 Gate

应用页严格按以下顺序推进：

1. **包完整性**：验证 schema、manifest、README、声明载荷、哈希、长度、重复路径、未声明文件和 Zip Slip。
2. **目标基线**：逐操作检查期望存在、期望缺失、条目类型、旧内容指纹和读取权限。
3. **平台能力**：验证目标库和事务目录可写、同卷目录移动、原子替换、链接边界、大小写和 Unicode 文件名行为。
4. **事务应用**：获得目标锁，建立 Journal 和备份，逐操作写入并验证，最终提交 Journal。

任一基线冲突都会返回冲突列表，不创建事务目录、不获得锁、不写入目标。应用按钮只在包检查完成、目标已选择且基线零冲突时启用。ApplyWorkflow 仍会在真正写入前重新执行包检查和基线验证，以避免用户审核后目标发生变化的 TOCTOU 风险。

## 事务与备份位置

每个目标库使用同级隐藏事务目录：

```text
<目标库父目录>/.<目标库名称>.vaultdelta-transactions/<operation-id>/
  journal.json
  backup/
```

该布局避免把 Journal 和备份纳入 Obsidian 库扫描，同时保证事务目录与目标库处于同一卷，满足删除目录通过原子移动进入备份的能力要求。Journal 路径会在应用结果中保留，可直接交给恢复入口。

## 失败与恢复

应用完成后状态为 `Committed`。如果写入、验证或故障注入导致事务中断，Journal 转为 `NeedsRollback`，界面突出展示错误和 Journal 路径，并启用恢复操作。

恢复入口也允许用户独立打开 `journal.json`。RollbackWorkflow 从 Journal 获得目标根、备份根和逐项状态，不依赖原补丁 ZIP；它按相反顺序恢复已完成操作，每项完成后持久化 Journal。恢复再次中断时，可使用同一 Journal 幂等重试。缺少备份或目标状态不可验证时停止，不猜测性覆盖数据。

## 界面状态

补丁工作区状态包括：空态、检查包、包就绪、检查基线、冲突、可应用、应用中、应用完成、需要恢复、恢复中、恢复完成和错误。

页面由两个并列任务卡组成：左侧是 Apply Gate，右侧是 Recovery。冲突列表独立显示冲突类型、相对路径和原因，并明确说明目标库尚未被修改。写入和恢复结果使用不同状态块，避免把成功应用与成功回滚混为一谈。

## 自动化和视觉验证

ViewModel 测试覆盖：

- 有效包检查及摘要。
- 基线通过后才启用 Apply。
- 冲突列表和零 Apply 调用。
- 中断应用暴露 Journal 和恢复入口。
- 无补丁包时独立 Journal 恢复。
- 损坏包错误状态。
- 比较结果调用真实补丁构建端口。

真实临时目录 E2E 覆盖从比较结果发布 ZIP，并用生产 `ZipPackageReader` 和 `PackageInspector` 重新验证。既有 Apply/Rollback E2E 继续覆盖全操作往返、基线冲突零写入、ZIP staging、能力验证阻断、故障注入和幂等恢复。
